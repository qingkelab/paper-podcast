# 画面渲染：HTML（Chrome 无头）与 SVG（resvg）两条路径

## 为什么要换

老路径是「Python 手算坐标 → 拼 SVG → resvg」：折行靠一张**近似字宽表**、
放不下就**试六档字号**、数字高亮的底色靠**手工累加每个字的宽度**、
图片等比缩放和居中自己算、封面标题块高和面板高度自己算。
那时三千多行的 `video.py` 里有相当一部分在做浏览器本来就会做的事，
而且做得**不如浏览器准**（它量的是真实字体度量）。

实测两个例子：

- 封面标题「4 比特反超 INT8，显存降七成」，老路径 `_wrap` 断成了
  「4 比特反超 INT8，显存降七 / 成」——最后一行只有一个字。
  同一个 `Layout`、同一份数据，浏览器一行就放下了。
- 数字高亮：老路径要先算出「这一段文字的像素宽」再在它下面垫一个圆角矩形；
  HTML 里就是 `<span class="num">67%</span>` 一个内联背景。

## 三档：决定「一页要渲染几帧」

| 档 | 做什么 | 成本 |
|---|---|---|
| **A 静态页** | 一页只渲染 **1 帧**，静止时长交给 ffmpeg 重复帧 | 整页 125ms / 图片卡 106ms / 字幕带 83ms |
| **B 内容驱动动画页** | 只对**动画窗口**逐帧抓取，之后停在末帧 | 约 74ms/帧（含 seek） |
| **C 时间轴** | concat / 混音 / 时长对齐仍然归 ffmpeg | 不变 |

**整片逐帧是不划算的**：250 秒 × 30fps = 7500 帧 ≈ 15 分钟 + 约 1.1GB PNG，
而整条管线现在只要 40~95 秒。

## 逐层成本（实测，936×1210）

| 图层 | HTML | SVG | 一集大概多少张 |
|---|---|---|---|
| 整页（骨架） | 125 ms | ~90 ms | 30~90 |
| 图片卡 | 106 ms | ~90 ms | 30~90 |
| 强调行 / 聚光灯 | ~60 ms | ~20 ms | 30~90 |
| 字幕带 | 80 ms | **14 ms** | **26~72** |

其中截图本身就占 42 ms，是 HTML 这边的成本地板。

**字幕带的数量原来被我估成 500 条、算下来要 40 秒，那是错的**（量了库里 7 集：
跨语言合计 26~72 条 —— `CAPTION_BEAT_MAX = 2`，绝大多数段根本不需要拆）。
按 40 条算，HTML 3.2s 对 SVG 0.6s，**只多 2.6 秒**。所以字幕带也搬过来了，
没有为它做「拼长图 + crop」那套批量优化 —— 那要等到字幕带真的涨到几百条
（放宽行数上限、或切成更碎的句子）才值得。

## 一条真实出片的实测（250 秒、36 段、936×1210）

```
19:54:17 画面渲染走 HTML（Chrome 无头）
19:54:31 已渲染 36 帧画面（片尾品牌卡 4，字幕分句 18 段，转场 16 处）   ← 渲染阶段 14 秒
19:55:09 视频已重新合成：36 帧 / 250.8 秒                                ← 整条 52 秒
```

`ffprobe`：视频 250.765s / 音频 250.931s（**长度对齐没破**）。

## 现在迁到哪儿了

**所有整页与图层都已经走 HTML**：骨架页、图片卡、强调行、字幕带、片尾品牌卡、图内聚光灯。
SVG（resvg）路径**原地保留**，角色从「唯一实现」变成「保底」——
没装 Chrome 的机器上仍然出得了片，测试默认也走它。

## Tier B：内容驱动动画页（逐帧抓取）

机制已经跑通：**页面里的 CSS/WAAPI 动画 → 只对动画窗口逐帧抓 → 当成图片序列喂给
ffmpeg**，序列播完由 `overlay` 的 `eof_action`（默认 repeat）停在末帧，片段总长仍由
`-frames:v` 说了算 —— **长度对齐不受影响**（有端到端测试盯着：抽帧量到聚光灯在成片里
真的在移动，且视频长度 == 音频长度）。

用到的接口：`focus_overlay_page(..., origin=...)` 生成动画页 →
`ChromeSession.render_frames` 抓 `FOCUS_MORPH_SEC × 30 = 14` 帧 →
`encode_video(focus_animations=...)` 挂 `-framerate 30 -i focus-XXXX-%04d.png`。

**动画窗口只有 0.45 秒（14 帧 ≈ 1 秒渲染）**。这就是这一档的意义：整片逐帧是
7500 帧 ≈ 15 分钟，只有内容真的在变的那一小段才值得逐帧。

### 两个原型都做过了，各自的结论（都是量出来的）

| 想法 | 结论 |
|---|---|
| **聚光灯从上一处移到这一处** | ✅ 已落地。位置差 < 0.02 不做（差一两个像素看不出来，白花 14 次渲染）；换图 / 进片尾 / 上一段没有聚光灯都不做 |
| **示意图「逐块长出来」** | ❌ **被数据否掉**。我们生成的信息图/段落示意图有 **34~53 个顶层元素**，按小节分组是 12~17 组：按 0.55s/组要 **9 秒**，而一段画面才 7 秒 —— 前几秒观众看到的是一张**半空的页面**（原型帧 t=1.1s 时只有标题）。压到 3 组虽然只要 1.05 秒，但那时它已经快到来不及看，等于没做 |

### ⚠️ 聚光灯移动在现有数据上一次都不会触发

量了库里 7 集：**相邻两段框同一张图**的情况只有 1 处，而那一处的两个框**完全一样**
（`moved = 0.0` —— 模型给连着讲的同两张图选了同一个子图）。所以这个动效目前是
「实现正确但从未触发」。要让它真的出现，得先让相邻段落的子图选择有变化
（那是 prompt / 数据的事，不是渲染的事）。

想加别的 Tier B 动效时，先拿这条尺子量一下候选：**动画窗口多长、这期间画面是否完整、
以及它跟正在讲的内容是不是同一件事**。前两条是硬指标（窗口太长=渲染贵，
画面不完整=观众以为坏了），第三条是产品原则（推拉镜头就是栽在第三条上）。

## 两条路径怎么共存

`video._render_scene_layers()` 是唯一的入口，它开着 `render_session(work_dir)`：

```python
with render_session(work_dir) as session:      # HTML 可用 → ChromeSession；否则 None
    _render_chrome_layer(..., session=session)  # session 是 None 就自己退回 render_chrome()
    _render_card_layer(..., session=session)
    _render_point_layer(..., session=session)
```

- `htmlframe.backend_name()` 是**唯一**的判据来源：`RENDER_BACKEND=svg` 强制走老路；
  要求 `html` 但机器上没有 Chrome 时**自动降级**（并记一条日志）。
  「这条机器没装 Chrome」不该变成「出不了片」。
- `RENDER_HTML_LAYERS=0` 可以单独关掉图层走 HTML（不必回滚代码）。
- 出片用的哪条路径存进 `video.renderer`（`html`/`svg`），**并且通过接口报出来** ——
  否则「同一篇论文两台机器出的画面不一样」光看 MP4 是查不出来的。
  （它一度只写库、不出口：既不在 `VideoInfo` 里，也没进 `_version_payload` 的
  白名单 —— 排查时给不出来的字段，和没有这个字段是一样的。）
- **测试默认走 SVG**（`tests/conftest.py` 里 autouse 设 `RENDER_BACKEND=svg`）：
  既快又确定。真正关心 HTML 的测试自己开（`tests/test_htmlpage.py`）。

## 页面与渲染器的约定

- **文字折行由 Python 定，不让浏览器/CSS 自己折**。封面大字标题的断点用
  `design.hook_lines` 算好（优先断在标点上），HTML 用 `<br>` 钉住、SVG 直接按行画 ——
  两条路径**共用同一个函数**，所以同一个标题在两条路径上断在同一处。
  交给 CSS 的话它只会按宽度折：「显存直降 68.7%！Qwen/Kimi 同款」会断成
  「…Qwen/Kimi」+「同款」，末行只剩一个词，读起来像话被截断。
  字号也一起算好传过去（`cover_title_layout`），`data-fit-*` 只作为 Chrome 度量
  和我们的估算不一致时的兜底。

- 页面必须**自包含**（图片走 data URI）—— 这样一份 HTML 丢到哪都能渲染出同样的画面，
  截图失败的现场也能直接丢进浏览器看。
- `window.prepare()`（可选、异步）：在「加载完 + 字体就绪 + 图片解码完」之后、
  第一次截图之前被 await。字号自适应（`fitText`）走这里。
- `window.seek(seconds)`（可选）：JS 动画的 seek 钩子。CSS/WAAPI 动画不用它 ——
  渲染器自己会 `document.getAnimations()` 全暂停再 seek。

## 迁移带来的两处实测收益

都不是猜的，是拿库里真实内容量出来的（脚本见本节说明）：

| 缺陷 | 老路径（Python/SVG） | 新渲染器（浏览器） |
|---|---|---|
| **标点被甩到下一行独占一行** | 404 条真实字幕里 **14 条**（3.5%）出现 `。` / `，` 单独一行（成片抽帧里亲眼见过） | **0 条** —— 中文排印不允许行首出现收尾标点，浏览器照做 |
| **图注能看到多少字** | 中位数 **160 字**（18px 硬切两行，末尾没有省略号，句子断在半截） | 中位数 **227 字**（+42%）：先缩字号再截，末尾带省略号 |

图注那一行要说清楚取舍：字号会从 18 压到 14（40 条里 20 条），换来的是一片地方多看到
四成字。图注是论文自己的原话（参考信息），不是解读本身 —— 这个交换是划算的；
要改就是 `_fit_attrs(max_font=18, min_font=14, ...)` 里那个下限。

**这两条都能被「量浏览器实际怎么断行」查出来**：逐字取 `Range.getClientRects()` 的 top
按行分组，就能得到每一行的**确切文字**（`innerText` 做不到 —— 它给的是整段）。
写这个工具时踩了一个坑：不能只取 `el.firstChild`，数字会被包成
`<span class="num">`，「6比特方案…」这种句子第一个子节点是元素不是文本节点 ——
必须用 TreeWalker 走所有文本节点。

## 配图装填：按「内容包围盒」放，而不是按整张图

论文插图导出时普遍带一圈白边（画布留白、页边距）。老做法是「整张图等比缩进
`image_box_w × image_box_h` 的卡片」——白边照样占地方，内容就被挤成卡片中间一条。
实测 896×742 的竖版卡：一张 962×440 的宽图装进去只占 410 px 高，**卡片空白行 39.9%**；
一张白边极大的插图更差，**73.5%**。

现在的做法是**只量不裁**（`video_render._ink_bbox`）：

1. 用 242 的阈值扫出「真的有墨」的矩形（整张全白 → 返回 None，退回老路径）；
2. 按这个矩形的宽高算缩放（内容一定装得进卡片），把它居中到卡片；
3. 图外那圈白边**溢出到卡片之外** —— 页面本来就是白底，看不见；
4. 细边框改成贴着**内容**走，而不是贴着画布（不然框里还是一大圈白，等于没改）。

不裁像素是有意的：`Pixmap(pix, irect)` 这个裁剪构造在 PyMuPDF 里不可用（实测直接
`TypeError`），而且裁像素一旦算错就**丢内容**，溢出白边最多是「不好看」而已。
溢出给了上限 `CARD_OVERHANG_RATIO = 0.25`（卡尺寸的 1/4）：阈值 242 和纯白 255 之间
只差 13 级，视频里看不出来，但万一某张图底色不是纯白（245 的浅灰页底），有这个上限
就不会露出一个淡淡的方块。

**实测**（真渲染出 PNG，按 alpha 合到白底后数纯白行；第一版忘了合白底，
透明像素转灰度成了 0，量出「0.0% 空白」这种假数据）：

| 图 | 卡片空白行（改前 → 改后） |
|---|---|
| 高瘦插图 100dce22-f1（472×618） | 10.1% → **0.0%** |
| 宽图 100dce22-f2（962×440） | 39.9% → 39.2% |
| 宽图 1bad491a-f2（997×345） | 56.3% → 54.9% |
| 白边极大的插图（1600×1200，内容 700×260） | 73.5% → **63.9%** |

**宽图几乎不变，这是对的、也是没解决的**：宽图受**宽度**限制（卡宽 896，已经吃掉
画幅的 96%），再放大只能裁掉内容。宽图剩下的那 40%~55% 空白行是**画幅比例**问题，
要动的是「卡片高度/字幕区跟着图的比例走」，不是装填规则 —— 两件事别混着改。

验收在 `tests/test_render_discipline.py::TestFigureIsFittedByItsContent`：造一张
「图小、白边大」的插图，断言按内容装填比按整张图明显放大、内容一个像素都不出卡、
边框贴住内容；再加一条 `_ink_bbox` 返回 None 的兜底（全白图不能崩）。

### 几何只有一份：`services/figure_fit.py`

装填那段几何原来是**只写在 SVG 那条路里**（`video_render._fit_figure`），HTML 那条路
交给浏览器的 `max-width/max-height` 自动缩。两条路看起来都对，**差在居中的是谁**：

- SVG 路居中**内容**；
- HTML 路居中**整张图** —— 图里烘进去的白边也算宽度。

实测 a1ed76d0 的 Fig.2（源图 1136×562，墨迹 `x 20~981`，也就是**左边 20px 白、右边 154px 白**）：
html 路上内容偏左 **67px**，卡片左右留白 8 / 69 —— 用户的原话就是「视频中的图片要左右居中」。
（那集的 `renderer` 是 `html`，所以成片里看到的就是偏的；SVG 路反而是正的，这种「换个后端
才现形」的偏差最难发现。）

现在几何搬到了 `figure_fit.fit_figure()`：`htmlpage._plain_image_block` 与
`video_render._fit_figure` 都调它，HTML 那边只负责把图按算好的偏移塞进一个「内容大小」的框。

**实测**（同一张图，两条路各自的左右留白，用一张 800×600、内容在 470~770 的合成图量）：

| 路径 | 左右留白 | 结论 |
|---|---|---|
| HTML（改前，浏览器缩整张图） | 526 / 86 | 内容偏右一大截 |
| HTML（改后，`figure_fit`） | 201 / 200 | 居中 |
| SVG（一直是 `figure_fit` 的算法） | 199 / 199 | 居中 |

验收入口：`tests/test_figure_fit.py`（墨迹包围盒、居中、溢出上限、**两条路径同一组数**）。

## 宽图：文字层跟着图的下沿走（以及「空白降不下来」这件事）

图片区是固定尺寸（竖版 912×742，`image_top=74`），而论文插图大多是**宽**的。
一张 962×440 的图装进去只占中间 400px 高：**图的下沿在 y≈645，而图注钉在 y=822** ——
图注离它描述的那张图 **348px**（实测）。观众看到的不是「一张带说明的图」，
而是「图在上面、说明在下面很远的地方」。

`design.content_layout(layout, figure_h, has_caption=…, has_point=…)` 把图注与强调行
挪到「图的下沿 + `FIGURE_CAPTION_GAP`」，图注顺手放大一档（18 → 22px，
`caption_line_height` 跟着算行高）。它返回一个**新的 `Layout`**，渲染各层与编码叠层
用的是同一个对象（`video.py::_scene_layout` → `RenderedLayers.layouts` →
`encode_video(scene_layouts=…)`），两处不会各摆各的。

**踩坑**：图片在卡里是**居中**的，所以内容下沿不是 `image_top + figure_h`，
而是 `image_top + (卡高 + 内容高) / 2`。第一版按前者算，图注被摆到 y=500 ——
**直接压在图上**（渲染出来量墨迹：图注 500~559，图占 245~645）。
这种错在 `content_layout` 的返回值里看不出来，必须渲染一帧量像素。

不变量（`tests/test_figure_reflow.py` 盯着）：图铺满卡片时返回值**逐字段相同**
（老片子重合成一模一样）；图注/强调行只许往上挪、绝不压图、绝不越过字幕带；
`figure_h=None`（封面 / 图解 / 读图失败）原样返回。

**实测（同一集 100dce22，同一套代码只切换这一个开关）**：

| 量什么 | 图注钉在卡片底边 | 图注跟着图走 |
|---|---|---|
| 图注离图的下沿 | 348 / 344 / 184 / 149 px（按图不同） | **26 px** |
| 内容区空白行占比（y < 字幕带） | 35.6% | 35.6% |
| 最长连续空白带 | 173 px | 256 px |

**第二、三行要说明白**：这一改**没有**让整帧的空白变少，反而把「最长的一段空白」
从 173px 变成 256px —— 因为原来那条钉在卡片底边的图注，正好充当了把空白**切成两段**
的分隔线。空白总量在两种版式下完全一样（35.6%）。

**为什么降不下来**：宽图受**画幅宽度**限制。912 的卡宽对一张 962 宽的图已经是
0.95 倍，再大只能裁掉内容。所以「宽图场景留白多」的根子在**画幅比例**，不在版式：
能做的是①把卡宽从 896 放到 912（左右各留 12px）：实测 962×440 的图从 896×395
变成 912×407（+1.8%），这已经是唯一能让宽图变大的杠杆；
②让文字紧贴图（这一节）；③**用别的内容去填**（图解镜头 / 「本段要点」行 / 局部放大镜头）。
③才是真正能把 35.6% 降下去的那条路，而它们都要**重新问一次模型**（存量集的
`preset` 里没有这些字段，「重新合成」按规矩不调模型，所以怎么重合成都不会出现）。

## 强调行固定在底部（它**不**跟着图走）

「文字层跟着图走」那一节只适用于**图注**。第一版把**强调行**（浅蓝底「本段要点」那一行）
也一起上移了，结果它在不同段里**上下跳**：宽图时跑到图下面（实测 y≈740），
窄图时仍留在 878 —— 同一个元素全片换位置，看起来就是忽上忽下。

用户的要求很直接：「高亮的文字位置不要靠上，放在底部，字幕上边就行」。
现在 `design.content_layout` **只改 `caption_top`**，`point_top` 一个字都不动
（`PANEL` 常量 `FIGURE_POINT_GAP` / `FIGURE_POINT_MIN_TOP` 一并删掉，免得后来的人以为它还在用）。

**实测（e3083750 重合成后，抽样 7 帧）**：强调行全都落在 **y 880–951**，
紧贴字幕带上沿（968）—— 改动前同一批帧里它是 740 / 832 / 878 三种位置。

不变量有测试盯着：`test_the_highlight_row_stays_at_the_bottom`（图高从 300 到 742，
`point_top` 必须始终等于基准值）与 `test_caption_never_moves_down`。

## 三条「约束静默失效」的教训（同一类 bug，三个实例）

字号自适应那套判据（`scrollWidth <= clientWidth` / `scrollHeight <= clientHeight` / 行数 ≤ N）
都依赖一个前提：**被量的元素有确定的尺寸**。三个实例全是这个前提没满足：

| # | 哪里 | 为什么判据恒为真 | 后果 |
|---|---|---|---|
| 1 | `window.prepare()` 压根没被调用 | 判据一次都没跑 | 所有文字停在 CSS 最大字号 |
| 2 | `.subtitle-text` 是 `height: auto` | `scrollHeight == clientHeight` | 136 字字幕停在 30px，末行越出页面 6px 被裁 |
| 3 | `.point-text` 宽度由内容决定（flex 子项） | `scrollWidth == clientWidth`（一起长） | 27 字强调行量到 900px，越出 856px 的底框**和画面右边缘**（实测） |

三条都修了，并且**每条配一个「量边界」的测试**，而不是「量有没有缩」：
- 字幕：`末行底边 <= 页高`
- 强调行：`文字右边缘 <= 底框右边缘`（竖版超长必须缩、横版放得下必须不缩）
- prepare：截图上方块必须在 `prepare()` 搬到的位置

真实数据里这三条**都没造成可见损坏**（216 条强调行都没溢出 —— 产品自己的 20 字上限挡住了；
249 条字幕最多 4 行，没到 6 行上限）。**但这正是它们难发现的原因**：
约束失效不报错、当前数据也不越界，只有在「文案变长」或「上限放宽」的那天才暴露。

### 量的时候踩的两个坑

- **别用 `scrollWidth`/`scrollHeight` 当判据去验证约束**：元素没有确定尺寸时它们会骗人，
  而这恰恰是 bug 本身。要量**边界矩形**（`getBoundingClientRect()`）。
- 元素给了固定高度之后 `scrollHeight` 会被钳到盒高，短文本会被误报成「5 行」
  （我在量字幕时就先被它骗了一次）。要数真实行盒：逐字 `Range.getClientRects()` 按 top 分组。

## 踩过的坑（都是实测）

- **必须 `--no-sandbox`**：默认沙箱在本机报
  `sandbox initialization failed: Operation not permitted`。
- **必须独立的 `--user-data-dir`**：跟正在运行的浏览器共用一个 profile 会失败。
- **`chrome --headless --screenshot` 写完 PNG 之后进程不退出**（看着像挂死 15 秒）。
  所以走 CDP，不用那条 CLI。
- **CDP 的 `Emulation.setVirtualTimePolicy({policy:"pause", budget})` 会报
  `Can only specify budget for non-Pause policy`**，而且虚拟时间**不推进 CSS 动画**
  （实测进度条一直停在 0px）。动画必须用 WAAPI seek。
- **`Page.setDocumentContent` 的文档源是 `about:blank`**，从那里加载 `file://` 图片
  会被拦掉（跨源）。我们所有页面都把图片内联成 data URI，所以不受影响 ——
  但**别**把图片改成按路径引用。
- **图层页必须显式关掉白底**（`Emulation.setDefaultBackgroundColorOverride`）。
  Chrome 默认给不透明白底，图层多带一整块白就会把下面那层整块盖掉，
  而画面看起来还是「白的」—— 不报错，只是别的东西全不见了。
- **图层页的区域元素必须重置到原点**。图层页的画布**就是**那一块区域，
  而 CSS 里 `.point-row` 的 `top` 是 `878px`（整页坐标）；不重置的话内容整个落在画布外，
  截出来是一张空图。
- **seek 之后要等两帧 rAF**（一帧让样式生效、一帧让合成器跟上）。少这一等会截到**上一帧**。
- **页面约定的 `window.prepare()` 必须真的被调用。** 曾经文档里写了约定、
  `_READY_SCRIPT` 里却没调 —— 于是「字号自适应」和「标签别出画」**一次都没执行过**：
  页面照样渲得出来、看着也正常，只是所有文字都停在 CSS 的最大字号上。
  这类「文档写了、代码没接」的缺口不会报错，只能靠**像素级**测试盯住
  （`prepare()` 把方块搬到右边，截图上就必须在右边）。
- **Chrome 要单独一个进程组，关的时候整组收掉。** 它的渲染/GPU 子进程不会跟着主进程
  一起退出，还会继续往 `--user-data-dir` 里写东西 —— 于是 `rmtree` 半路失败，
  而它是 `ignore_errors=True`，**静默**留下一个 `paper-podcast-chrome-*` 临时目录。
  实测跑几次测试就能攒下一堆（现在 `start_new_session=True` + `killpg` + 重试删除，
  跑完一遍测试进程与目录残留都是 0）。
- **Playwright 装浏览器在这台机器上超时**，别走它。
- **截图本身占 42ms**（936×242 的 PNG），这是每条字幕带 83ms 里的大头 ——
  换 JPEG(95) 只快 4ms，不值（文字边缘还会有压缩痕迹）。

## 横版 / 竖版（两种画幅并存）

同一个渲染管线支持两种画幅，**换朝向只换数值，不换阅读顺序** ——
版式都是「图片区 → 图注 → 强调行 → 字幕带」这一条纵向流（顶部原来那行论文标题已去掉，见「标题与封面」一节），
所以两版看起来是同一个产品，而不是两种风格。

| | 画幅 | 文件 | 字段 |
|---|---|---|---|
| `portrait`（默认） | 936×1210 | `<id>.mp4` / `<id>.<lang>.mp4` | `video` / `video_path` |
| `landscape` | 1920×1080 | `<id>.landscape.mp4` | `video_landscape` |

- **竖版的名字与字段一个字都没改**：老链接、老缓存、老客户端全都不受影响。
  横版是**额外产出**，永远不会顶掉竖版 —— 存储上就是两个不同的键
  （`video` vs `video_landscape`）。踩过的坑：给单语言集（没有 `versions`）加横版后，
  接口一直返回 `null` —— 因为「老数据兜底」那段代码把顶层字段拼成版本时
  **没有把 `video_landscape` 带进去**，而顶层 `to_episode` 也漏了这个键。
  两个地方都要加。
- **`Layout` 是 dataclass，不是一堆全局常量**：`PORTRAIT` / `LANDSCAPE` 两个实例，
  渲染函数一律收 `layout: Layout = PORTRAIT`。老代码里那些 `VIDEO_W` / `SUBTITLE_TOP`
  之类的常量保留成**竖版的别名**，测试和别处直接引用的地方不用改。
- **`_rasterize_custom` 必须显式传 width/height**：resvg 是按宽度缩放、高度按比例推的，
  渲染 896×742 的图片卡时传 `width=936` 会得到 936×776。
- **横版编码更慢是正常的**：像素数是竖版的 2.4 倍，实测同一条 250 秒的片子
  竖版约 50s、横版约 168s。
- **画幅是每集各自的产物**：切集/切语言要复位到竖版，否则会拿着上一集的画幅状态。
  前端只有在**真的存在**那一份时才给切换器，没有就给一个「生成横版」按钮
  （点了能出东西的按钮，比一个点了没反应的开关强）。
