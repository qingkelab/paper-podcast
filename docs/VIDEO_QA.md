# 成片自查与响度：**只有成片里才看得出来的那三件事**

分层测试能证明「字幕会换、动效会动」，但证明不了「整条片子里有 10 秒什么也没发生」——
那是**时间轴上的性质**，不是某一帧的性质。所以合成完输出之后，还要对**成片本身**量三样：

| 量什么 | 为什么它只能在成片上量 | 实现 |
|---|---|---|
| 画面有没有长时间不动 | 需要按时间轴抽样比对，单帧测试看不见 | `video_qa.find_static_gaps` |
| 响度够不够 | 归一化是在 ffmpeg 里做的，**写对滤镜串 ≠ 生效** | `loudness.measure_loudness` |
| 音画长度差 | `-shortest` 的结果只有封装完才知道 | `video_qa.qa_video(audio_path=…)` |

结果存进 `video.qa`（跟着 `VideoResult.to_dict()` 一起进库），日志里同时打一行摘要 +
「最严重的 3 个问题」。命令行也能单独跑：

```bash
cd backend && ../.venv/bin/python -m app.services.video_qa ../data/videos/<id>.mp4 <音频路径>
```

## 静止空档：判据是标定出来的

做法：`ffmpeg -vf fps=2,scale=64x36:flags=area,format=gray -f rawvideo -` 把片子解成
一串 64×36 灰度帧，在 Python 里逐对比较（纯标准库，224 秒的片子约 1.7 秒）。

**「变了多少像素」的门槛**用真实成片 + 库里存的段起始时间标定过（字幕是按段换的，
所以段起点就是「该有新东西」的时刻）：

| 变化比例（灰阶差 >12 的像素占比） | 出现对数（100dce22，447 对） | 这是什么 |
|---|---|---|
| 恰好 0 | 197 | 真的一个像素都没变 |
| < 0.001 | 68 | 进度条在爬 |
| 0.001 ~ 0.003 | 56 | 进度条 + 声波条 + 淡入中间帧 |
| 0.003 ~ 0.006 | 24 | 噪声与信号混在一起的一档 |
| **≥ 0.006** | 102 | **字幕换句 / 强调行 / 换图**（其中 59% 落在段起点 ±0.75 秒内，随机基准 22%） |
| ≥ 0.02 | 65 | 整块换图、片尾卡这种画面级变化 |

门槛因此定在 **0.006**（`CHANGE_RATIO`）：放宽到 0.003 会让事件数从 102 涨到 126，
多出来的那批只有 40% 落在段起点附近 —— 就是噪声。

**按这条量出来的现状（三条真实成片）**：

| 集 | 落在「≥4 秒无可见变化」里的时长 | 最长的一段 |
|---|---|---|
| 100dce22 | 52.5% | 11.5 秒 |
| 666adf5b | 58.0% | 9.5 秒 |
| 4e594ee2.en | 67.7% | 11.0 秒 |

也就是说参考做法里那条「每 2–4 秒画面上要有新东西」的规矩，**我们目前是不达标的**。
空档本身不是 bug（一句 30 字的话本来就要念 10 秒），但它现在是一条**可量的指标** ——
先能量，才谈得上改不改、改哪里。报告给的是「最长的那 3 段 + 时间点」。
抽样时间点的精度是 `1/fps`（0.5 秒），别拿它当帧级证据。

## 响度：能到 -14 就到，到不了就守住 true peak

目标 `-14 LUFS / true peak ≤ -1.5 dBFS`（`loudness.TARGET_*`），在**封装那一步**
用两遍法的 `loudnorm` 做（`normalization_chain` 先量一遍、把 `measured_*` 填进第二遍）。
放在这一步是因为那是唯一处理音频的地方，不用多一次转码。

**实测现状（真实成片，不是推算）**：

| 集 | Integrated | True peak | 峰均差 |
|---|---|---|---|
| 100dce22 | **-18.1 LUFS** | -1.4 dBFS | 16.6 dB |
| 666adf5b | -18.4 LUFS | -1.4 dBFS | 16.9 dB |
| 4e594ee2.en | 更低（RMS -22.9） | -4.1 dBFS | 18.9 dB |

两件事值得记下来：

1. **同一套流水线出来的集，响度能差 4~5 LU** —— 用户连着听两集要来回拧音量，
   这才是归一化真正要解决的问题。
2. **-14 LUFS 在一部分素材上「到不了」**：100dce22 要到 -14 得加 +4.14 dB，
   而它的 true peak 已经在 -1.4 dBFS —— 加完峰值 +2.7 dBFS，必然削波。
   **这是 ffmpeg 自己的结论**：两遍法的 JSON 里 `target_offset: 1.70`、
   `output_i: -15.70`（单遍 dynamic 也是同一个数 -15.7）。
   要真踩到 -14 只能上压缩（那 1% 最响的样本只比峰值低 1.2 dB，会被压得很勤），
   那是**会听得出来的音色改动**，不在「归一化」的范围里，需要单独决策。

所以策略是：**能到 -14 就到 -14，到不了就把 peak 守在 -1.5 dBFS 上停住**，
并把「差多少」记进报告（`below_target_lu` / `target_offset_lu`）。

**真实成片改造前后（同一集 f7c8af00，改完当场重新合成量的）**：

| | 改之前 | 改之后 |
|---|---|---|
| Integrated | -17.8 LUFS | **-15.5 LUFS**（+2.3 dB） |
| True peak | -1.5 dBFS | -1.0 dBFS |
| 静止空档占比 | 59.2% | 59.6% |

两句话要说清楚：**响度确实抬起来了**（+2.3 dB，离目标还差 1.5 LU）；
**空档指标没有变好** —— 这一轮做的是「让这类问题第一次变得可量」，
不是「把它压下去」，弹簧动效对「≥4 秒无变化」的计数几乎没有影响。
另外注意 true peak 落在了 **-1.0 dBFS**（比目标高 0.5 dB）：这是 loudnorm 动态模式的
已知行为（它优先保响度），远没有削波，但如果以后要严格守 -1.5，得在它后面再挂一个限幅器。

**静音不是「很轻的声音」**：ebur128 对数字静音报的是 `I: -70.0 LUFS`（它的下限），
拿它算增益会得到「+56 dB」这种荒唐结果。低于 `SILENCE_LUFS = -60` 一律当**测不到**，
调用方退回原行为（不假装测到了）。

## 端到端怎么验

`tests/test_video_qa.py` 里两条是核心，都不是「字符串里有这个字段」：

- `test_a_frozen_picture_is_detected`：真的编一段 6 秒不动的画面 → 空档必须被抓到；
  反过来 `test_changing_content_is_not_flagged`：每 1.5 秒换一次颜色 → 不许误报。
- `test_encoding_actually_raises_the_loudness`：造一段振幅 0.03 的音轨，
  出片**再量一遍**，响度必须被抬起来，且 true peak 不越线 ——
  这是唯一能证明「归一化真的进了 MP4」的断言。
